2.What was built

The back end for this assignment is the group chat application from the previous assignment. It is the persistent encrypted chat from csd-group-chat, running as three copies instead of the simple HTTP server used in the tutorial slides. A stateless server would work behind a round robin proxy without changes. A chat server does not, so three things were needed.

  1. One shared database. All three copies use the same MongoDB on Sys1. Chat history and the stored public keys are therefore the same wherever a client lands.
  2. A shared broadcast channel. Socket.IO keeps connections in the memory of one process. A message sent to the copy on Sys2 would never reach a client on Sys4. The official MongoDB adapter gives the three processes a channel to publish broadcasts on.
  3. Sticky sessions in the load balancer. The Socket.IO handshake is a set of HTTP polls that only one process can answer. Round robin breaks it, so the load balancer keeps a client on one back end using a cookie.

3.Load balancer code (Sys1)

The design follows the tutorial. There is a list of backend structs, each holding a reverse proxy. A mutex protects the round robin index. A background loop checks health. The endpoints /lb/status, /lb/metrics and /lb/reset allow the experiments to be run again without restarting the process. Four things were added for this deployment.

AdditionReason
Sticky cookie
lb_backend		The Socket.IO handshake spans several requests and only one process can answer them. A client with no cookie is round robined and given one. A client with a cookie keeps its back end until that back end dies, and then falls back to round robin.
Connection pool
MaxIdleConnsPerHost: 256		The default transport keeps only two idle connections per host. Above a low rate almost every request opened a new TCP connection. That held the proxy at 443 req/s while the back ends served 1244 req/s on their own. Fixing it raised the proxy to 674 req/s on the same test.
TLS
-tls-cert and -tls-key		The chat client signs its login with WebCrypto. Browsers only allow WebCrypto on a secure origin. Over plain HTTP the app loads but nobody can log in.
Three failed checks before marking downOne slow reply is not a dead server. A back end is only removed after three failed checks in a row.
Round robin is still what the experiments measure. Both load generators run without a cookie jar, so all of their requests take the round robin path. Stickiness only affects browsers and Socket.IO clients. This is why the split across back ends in Section 7 comes out even.

4.Back end deployment (Sys2, Sys3, Sys4)

Each system runs the group chat server with the patch below and nothing else changed. Node 24 was installed from the official tarball into ~/node, because there is no passwordless sudo on these containers and nothing could be installed system wide.

The patch makes two changes. The first attaches the Socket.IO MongoDB adapter so a broadcast from one copy reaches clients on the other two. The second adds an X-Backend header naming the copy, so a response can be traced to one machine. The encryption, the signatures, the stored public keys and the rate limiter were all left alone.

MongoDB runs as a single node replica set because the adapter reads a capped collection using a change stream, and change streams need an oplog that a standalone mongod does not have. The same database also holds the chat history and the public keys that all three copies share.

5.Load generators (local system)

Two load generators run on the local PC. Both are worker pools over a fixed number of requests and both write the same JSON and CSV. They exist because they measure different things.

GeneratorOne request isWhat it measures
HTTP
loadgen_main.go		 GET /health The path itself. The back end answers from memory in microseconds, so this measures the proxy and the network rather than the servers.
Chat
chatload_main.js		 A full chat session opening. It connects over WebSocket, signs the server challenge with ECDSA, logs in and waits for the chat history. The back ends. Before replying, the server decrypts and verifies the signature on all 100 stored messages. This is real CPU work.

The chat generator uses the websocket transport only. A websocket connection is a single request, so each session lands on one back end and the split stays even without needing the sticky cookie.

The room holds 120 seeded messages. History is capped at 100, so every login in the experiments does 100 decrypt and verify operations. An empty room would make that step free and the experiment would only measure the network. The seeded messages are written the way the server writes a live one, so they verify in the same way.

9.Observations

The chat workload scales with the number of back ends. Three back ends served the same 600 sessions 2.7 times faster. The median latency dropped by 71% and the p99 tail dropped by 41%. Both runs finished with zero failures, so this is a result about capacity and latency and not about errors. The work here is CPU bound on the back ends. Each login decrypts and verifies 100 stored messages on a single vCPU. Spreading 30 concurrent clients over three machines gives each machine about a third of the work. The gap below a perfect 3x is the time spent in the load balancer and in the shared database, which both sit on Sys1 and are not replicated.

The HTTP workload does not separate the two setups. This is the expected result and not a broken measurement. A GET /health costs the back end almost nothing, so the back ends are not the limit. The limit is the single vCPU on Sys1, which the load balancer shares with mongod and which also handles TLS. Adding back ends does not raise that limit. Each setup was run three times to check this. One back end gave 611.9, 725.8 and 729.3 rps. Three back ends gave 643.1, 602.3 and 865.6 rps. The two ranges overlap completely, so the 11% gap between the medians in the table means nothing.

The back ends really were less loaded even so. The proof is on the load balancer side of the hop, where the measured p50 dropped from 30.1 ms to 15.9 ms. The back ends answered in half the time, and none of that reached the client. This is the point the comparison was meant to show. A load balancer only adds throughput when the back ends are the bottleneck. On a cheap request the proxy is the bottleneck instead, and extra machines add nothing.

The client side tail got worse on the HTTP run, rising from 113 to 165 ms at p95 and from 178 to 290 ms at p99. With three back ends the proxy keeps three connection pools instead of one and runs three health checks per interval instead of one, on a vCPU that was already full. This is a real cost of spreading out and it shows up only because this workload has no other bottleneck to hide it.

11.The group chat application through the load balancer

The assignment asks for the group chat application to be reached through the load balancer. https://10.1.75.53:3229 serves the chat application and every request to it is passed to one of the three copies on Sys2, Sys3 and Sys4.

Getting a real time application to work correctly behind a round robin proxy needed the three pieces described in Section 2. The test below checks all three against the live URL.

  1. Two clients are put on different back ends and each one runs the real ECDSA login.
  2. One sends a signed message and the other receives it. This only works if the broadcast crossed machines, which means the MongoDB adapter is working.
  3. A third client on the remaining back end loads history from the shared database and gets the message back. It decrypts, and both the integrity tag and the signature verify. This shows the encryption key and the stored public keys are shared across all three copies.
